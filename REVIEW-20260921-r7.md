## 1. I/O-PSI-aware writeback admission

### Decision and execution sequence

The existing memory-pressure daemon and cold-maintenance timer continue to use the same policy entry point. A small `Zram::IOPressure` module reads host `/proc/pressure/io` before planning. The normal cold-page, tier, memory-state and writeback-quota gates remain in force. Eligible configured recompression operations execute first. Immediately afterward, before issuing any writeback trigger, the implementation samples I/O pressure again and re-reads the available quota.

The second sample addresses pressure that changes while candidate discovery or recompression is running. A new high-pressure sample reduces the already selected page ranges. All writeback specifications in the pass consume one shared remaining-page counter; an individual range or a later tier cannot restart the allowance. The final pass can never grow beyond its initially selected page cap. If I/O pressure recovers, the concurrency knob may return to the ordinary state limit, but this does not expand that pass's initial total page cap.

| Memory state | I/O state | Result with shipped policy, before stricter existing limits |
|---|---|---|
| Normal | Any | Existing normal cold maintenance; recompression only, no automatic disk writeback |
| Pressure | Low | Existing pressure policy: up to 64 in-flight operations and 8,192 selected pages |
| Pressure | High or unknown | Recompression first; at most 8 in-flight operations and 1,024 selected pages |
| Emergency | Low | Existing emergency policy: up to 128 in-flight operations and 32,768 selected pages |
| Emergency | High or unknown | Recompression first; still permit eligible writeback, bounded to 16 in-flight operations and 4,096 selected pages |

Every figure is an upper bound, not a promised amount of work. Existing configured maximums, backing-device queue depth, rotational-device limits, per-class candidate limits, actual eligible cold pages and remaining kernel quota can reduce it further. Emergency handling does not bypass quota exhaustion, cold-page eligibility, an unavailable authoritative candidate snapshot, or the policy enable flags.

The kernel distinguishes `writeback_batch_size` (maximum in-flight operations) from its writeback quota. The implementation consequently limits both concurrency and total selected pages; reducing the concurrency knob alone would not bound the pass. These are not a MiB/s rate limit. The existing systemd I/O/resource settings are retained. On a 4 KiB-page system, 1,024 and 4,096 selected pages correspond to at most 4 and 16 MiB of page data, not measured flash writes. Kernel writeback quota and backing statistics use fixed 4 KiB units. [S1]

### Conservative failure behavior

The sample reader allows at most 4,096 bytes, requires a regular opened file, uses no-follow/nonblocking flags and closes the descriptor on every path. It validates both records, all three percentage fields, duplicate/missing data and impossible `full avg10 > some avg10` values. Percentages use fixed-point integers, not binary floating-point threshold comparisons. Symlinks, FIFO/directory input, missing interfaces, malformed data, read failure and oversized input produce `unknown`, never a fabricated zero-pressure result.

With this policy enabled, unknown telemetry receives the same bounded limits as high I/O pressure. It does not crash the daemon or prevent all emergency relief. If the optional kernel batch knob is absent or rejected while throttling is required, the implementation caps the *entire synchronous pass* to the effective batch size. That fallback is at most 8 pages in pressure and 16 in emergency, or less if existing queue/resource limits are stricter. There is no fallback to an unbounded `type=idle`/`type=huge` writeback.

The root diagnostic `writeback-spec` command is also guarded. Under high/unknown I/O pressure it requires explicit page indexes/ranges, rejects broad type selections and refuses a request exceeding the admitted cap. It does not silently rewrite an operator's request. Under low I/O pressure its earlier diagnostic behavior is retained. The existing runtime lock continues to serialize maintenance and explicit writeback.

### Configuration and integration

All ten profiles explicitly declare these policy defaults; installer templating, the installed configuration, the schema and the validator agree:

```sh
ZRAM_IO_PSI_ENABLE="1"
ZRAM_IO_PSI_SOME_AVG10_THRESHOLD="10.00"
ZRAM_IO_PSI_FULL_AVG10_THRESHOLD="2.00"
ZRAM_IO_PSI_BATCH_SIZE_PRESSURE="8"
ZRAM_IO_PSI_BATCH_SIZE_EMERGENCY="16"
ZRAM_IO_PSI_MAX_PAGES_PRESSURE="1024"
ZRAM_IO_PSI_MAX_PAGES_EMERGENCY="4096"
```

They render into the `[io_pressure]` section of `/etc/zram-writeback.conf`. High I/O pressure means `some avg10 >= 10.00%` **or** `full avg10 >= 2.00%`. These are conservative, configurable initial policy choices, not hardware-calibrated performance claims. The kernel's PSI averages describe recent stall-time percentages, not instantaneous device utilization. The host-wide sample can include pressure on another storage device and cannot predict a spike after admission. [S2]

The validator rejects invalid booleans, nonpositive/invalid caps, invalid percentage values, pressure limits above their emergency counterparts, and I/O-pressure limits above the ordinary corresponding state limits. Explicitly disabling this optional policy skips I/O sampling and retains the earlier memory/tier policy. The explicit installer Perl-module inventory includes the new parser. A regression invokes the real module-staging function with temporary-file transport under dash, bash and BusyBox, comparing all 45 module paths, bytes and installed modes against the source library. No second daemon, new periodic timer, persistent queue, source build or additional AppArmor permission was added. The existing maintenance profile already permits reading the required I/O PSI file.

### Logging and metrics

Writeback-admission records are emitted at `info` through the existing managed zram route:

```text
/var/log/managed/zram/zram.log
```

They include memory state, I/O state/reason, sampled `some`/`full` values in millionths of one percentage point, `recompression_first`, effective batch size, whether the batch knob was applied, admitted page limit and selected page count. Thus `10000000` represents 10.00%, not ten million percent. The earlier per-operation writeback/recompression logs continue to report observed backing-counter changes and timing.

The actual on-disk metrics snapshot, normally `/run/zram/zram0.metrics`, also serializes:

```text
io_psi_state
io_psi_reason
io_psi_some_avg10_millionths
io_psi_full_avg10_millionths
```

Unknown observations remain the literal `unknown`. Tests check the serialized snapshot and emitted log, not only an in-memory hash. These are operation/snapshot records, not a new high-frequency log of every polling iteration. The configured `info` level is necessary to retain the new admission records. The existing local-syslog/stderr fallback, rotation and permissions remain unchanged. When a profile places `/var/log` on tmpfs, that text log remains volatile across reboot; this revision does not promise durable forensic retention.

## 3. Managed-application source review

All 23 `.py` files in `labwc_managed_app/` were read. The machine-readable review lists every module, review scope, original/current hash and changed status. Four modules required changes:

| Module | Narrow repair |
|---|---|
| `commands.py` | Normalize one-/two-dash switch names for validation, compare the name before `=`, reject sandbox-disabling boolean variants including `=false`, require explicit values for controlled platform/feature switches, and prevent value-form GPU-disable bypasses. Payload arguments are not rewritten. |
| `generic.py` | Apply the same single-dash normalization when filtering unsafe Electron switches and controlled platform/feature overrides. Preserve non-Electron handling, user-manager service ownership and the existing required outer-sandbox compatibility exception. |
| `user_state.py` | Reject dangling-link escapes before creation; initialize managed files through exclusive/no-follow descriptors; validate ownership, regular-file type and a single hard link on the opened inode; copy seeds through validated descriptors; only remove the created inode after failed initialization; bound JSON reads even when a file grows after its size check. |
| `sandbox.py` | Validate the requested persistent directory's HOME ancestry before `makedirs`, so a pre-existing symlinked parent cannot create a directory outside HOME before rejection. No other function was changed. |

The argument checks account for Chromium's support for one- and two-dash switch prefixes. Existing explicit compatibility exceptions are preserved rather than pretending every application has an identical sandbox. [S3] File-descriptor operations bind checks and changes to the opened file, while no-follow/exclusive open flags and bounded reads close the specific link/read gaps identified here. [S4]

Nineteen modules remain byte-for-byte unchanged. Exact source-segment comparison confirms that all 37 other functions in `sandbox.py` are unchanged, including the persistent sandbox argument builder and private compatibility lifecycle. Both private compatibility modules and declarative app profiles are unchanged. The comparison additionally verifies 222 protected unit, AppArmor, launcher and compatibility-related files against R6.

## 5. Target acceptance and publication

Publish the complete tree atomically so the preseed checksum, payload, manifests, profiles and served scripts cannot come from mixed revisions. Rebuilding the delivery payload is packaging, not compilation of third-party software. An existing installed machine also needs the matching rendered configuration and managed-package trust manifests; do not copy individual Python modules into a manifest-validated package and expect them to be accepted.

After installing the matching revision, these inspection commands do not force a writeback pass:

```sh
sudo /usr/local/libexec/zram-writeback validate-runtime
sudo /usr/local/libexec/zram-writeback status
cat /proc/pressure/io
sudo systemctl status zram-setup.service zram-writebackd.service --no-pager
sudo tail -n 100 /var/log/managed/zram/zram.log
sudo grep '^io_psi_' /run/zram/zram0.metrics
sudo cat /sys/block/zram0/writeback_batch_size
sudo cat /sys/block/zram0/writeback_limit
```

An optional unavailable kernel batch knob is a reported degraded condition, not proof that installation failed: verify that the bounded whole-pass fallback appears when throttling is needed. The snapshot may not yet exist before the first maintenance snapshot. Use the configured device/runtime names if the defaults were changed. Check service journal and AppArmor denial logs as well as the managed text log, and confirm all declared Perl/runtime dependencies are installed before interpreting startup results.

Hardware acceptance still needs a controlled low-I/O, high-I/O and emergency-pressure exercise while observing actual application responsiveness, quota behavior and backing counters. It should confirm stop/restart cleanup and native/private-compatibility application launches on Forky/systemd 261.2. Do not run an uncontrolled memory exhaustion test on a machine containing unprotected work. No live target installation, physical-device writeback test, or actual systemd 261.2/AppArmor enforcement run was performed in this container.
