## Root cause and repaired installation path

Revision 3's `ExternalSoftware::Servicing::Tomat::_release` accepted only an asset literally named `tomat_amd64.deb`. The supplied release instead names its amd64 Debian package `tomat_2.13.0-1_amd64.deb`. The existing selector therefore found zero matching assets and aborted. This was a filename-selection failure, not evidence that upstream lacked an amd64 package.

`baseline-failure-reproduction.json` records execution of the actual R3 and R4 `_release` method bodies against the same versioned-asset fixture: R3 produces the reported `Tomat release has no unique amd64 Debian asset` error; R4 accepts the correct filename, URL, tag and digest. The fixture's size is explicitly synthetic, not a claim that the vendor package was downloaded.

The installation path no longer discovers Tomat through `releases/latest`. All 13 files under `d-i/forky/hosts/profiles/` now contain these literal values:

```sh
SOFTWARE_TOMAT_TAG="v2.13.0"
SOFTWARE_TOMAT_URL="https://github.com/jolars/tomat/releases/download/v2.13.0/tomat_2.13.0-1_amd64.deb"
SOFTWARE_TOMAT_SHA256="871ee4fd19f3367cf4aa638a2364ae83de6c4ce4550a7ebe5ee6124be86c6aa1"
```

`software.sh` requires the three profile values and passes them as separate quoted arguments to the target's existing Perl adapter. `download_pinned()` validates the pins before making a Tomat HTTP request, uses the exact URL, and does not query a latest-release API or derive the expected digest from a remote response.

The adapter accepts only a bounded `vMAJOR.MINOR.PATCH` tag and a matching canonical URL in `github.com/jolars/tomat`, with a numeric Debian packaging revision and the `_amd64.deb` suffix. Alternate origins, credentials in URLs, query strings, fragments, mismatched tags or filenames, other architectures and malformed digests are rejected. Invalid pins do not trigger a fallback or a different release download.

The existing HTTPS transfer implementation, redirect host checks, transport deadlines and bounded transport retries remain in use. The allowed final hosts remain GitHub and its existing approved release-asset hosts. Bootstrap transfers are limited to 65,536 through 134,217,728 bytes; the complete file must then match the independently supplied profile SHA-256. No guessed exact byte length or extra byte-count profile setting was added.

After hashing, the existing Debian validator checks package framing, package identity `tomat`, architecture `amd64`, the expected executable path and its executable presence, and the package metadata. R4 additionally requires the package's exact Version to match the filename, `2.13.0-1`, rather than merely sharing the upstream `2.13.0` prefix. Nothing is installed when this validation fails.

The existing stock system/user service masks, managed repository installation, and post-install `tomat daemon run --help` / `tomat watch --help` checks remain. The session-scoped Tomat controller and Waybar menu commands are unchanged. The software add-on selection and existing amd64/arm64 installation policy are unchanged; these pins do not broaden platform support.

## Update compatibility without changing update policy

The two existing update paths had the same obsolete filename assumption. The Perl latest-release adapter and Tomat-specific handling in `local-apt-repository` now recognize a tag-matching versioned amd64 Debian filename, while retaining the legacy unversioned spelling for compatibility.

Release discovery still requires a unique applicable asset, the approved repository URL, the existing size bounds and a valid SHA-256 digest. Ambiguous releases are refused rather than selecting an arbitrary Debian revision. Both versioned and legacy filename metadata are covered by tests, including multi-architecture releases and duplicate assets.

Previously saved Tomat source records carrying the legacy filename hint can recognize the versioned replacement. That compatibility exception is limited to the exact Tomat GitHub releases API source and does not apply to unrelated repositories. Versioned candidates must match the downloaded Debian package's entire advertised version, including the packaging revision.

These are bootstrap pins, not a request to disable subsequent managed updates. Existing refresh scheduling, APT maintenance, update configuration, service ownership and authorization remain unchanged. No new updater, timer or fallback installation channel was introduced.

## Publishing safeguards

`tools/build.py` validates all desktop profiles before writing generated installer products. It rejects missing, empty, duplicate, unknown or non-literal Tomat pin settings, invalid tags, mismatched URL/tag/architecture/revision combinations and malformed hashes. It also rejects an absent profile directory. A coherently updated future release remains possible without changing the validator; its actual checksum must still be established by the maintainer.

The normal repository build regenerated `d-i/forky/payload.tar.gz`, `d-i/forky/payload.manifest` and `d-i/forky/preseed.cfg` together. An independent payload verifier checks every source byte, payload member, manifest hash, normalized payload permission and generated preseed pin.

Publish the complete repository atomically. Do not combine the R4 profiles or adapter with R3's generated products. Start a fresh installer run against the published R4 tree: changing the server does not update an R3 payload already loaded into an installer session. This release is a serving repository, not an in-place repair command for an existing installation.

## Validation scope and limitations

The new regression suite checks profile-to-installer argument transport under both Dash and BusyBox for all 13 profiles, pin validation before HTTP, actual SHA-256 verification, actual `dpkg-deb` metadata/payload inspection, version and architecture mismatches, oversized/truncated/symlink archives, failure before package installation, and both update discovery paths.

The Debian archives used by the regression suite are clearly labeled synthetic fixtures, not copies of Tomat. They contain no compiled vendor code; `dpkg-deb` packages the fixture files solely for validation. The offline method harness executes the actual production Perl method bodies and core modules, replacing only HTTP and object construction/accessors. It is not an emulation of Moo and is not counted as a full Moo/MooX application test. A separate full-module test is dependency-gated.

The validation container has Debian 13 (Trixie), Python 3.13.5, Perl 5.40.1 and systemd tools 257.9. The final full test run uses `/opt/pyvenv/bin/python3`, which already provides PyYAML for the existing config-safety tests; the earlier `/usr/bin/python3` runs did not have that dependency. It lacks the Moo/MooX validation dependencies; that limitation is reported as skips, not hidden or converted to passes. The target's existing dependency selections were not changed.

GitHub's published release asset listing was checked and agrees with the user's filename and SHA-256. The primary listing is:

```text
https://github.com/jolars/tomat/releases/expanded_assets/v2.13.0
```

The container could not download the vendor `.deb`: curl could not resolve GitHub, and the separate download tool also failed. Consequently the vendor package bytes were not independently hashed here. Published-digest confirmation and successful hashing/validation of synthetic test archives are separate evidence, recorded as such in `upstream-verification.json` and the test logs.

No complete Debian Forky/systemd 261.2 installation or live labwc/Mako session was booted in this environment. No kernel-enforced AppArmor or real power action was exercised. These limits apply even though the reported asset-selection bug was reproduced and repaired in the actual code paths.
