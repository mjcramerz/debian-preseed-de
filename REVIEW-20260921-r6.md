# Profile, storage and zram review - R6, 21 September 2026

## Scope and delivery

This revision addresses the requested profile names, physical-capacity sizing,
raw-zram alignment failure, zram pressure handling and audit visibility, and
zram helper isolation. It retains the complete served repository and regenerates
`d-i/forky/preseed.cfg`, `payload.manifest` and `payload.tar.gz`. No third-party
source patches or new source-compilation steps were introduced.

The deployment target is the user's Debian Forky/systemd 261.2 environment.
Validation here is non-destructive and runs in a Debian 13 container, not that
installed environment. The generated validation report records the distinction.
No claim of a completed installation, calibrated SSD performance, or formal
security certification is made.

## 1. Canonical profiles and safe multi-OS selection

The shipped inventory is ten remaining environment files (after the later profile retirement):

| Storage / hardware | Normal profile | Multi-OS profile |
| --- | --- | --- |
| Btrfs, generic NVMe | `btrfs-de.env` | `btrfs-de-duo.env` |
| Btrfs, P15s | `btrfs-de-p15s.env` | `btrfs-de-p15s-duo.env` |
| Btrfs, Flex | `btrfs-de-flex.env` | `btrfs-de-flex-duo.env` |
| F2FS, x360 | `f2fs-de-x360.env` | `f2fs-de-x360-duo.env` |
| F2FS, HP14 | `f2fs-de-hp14.env` | `f2fs-de-hp14-duo.env` |

The corresponding ten named profile classes, class catalog, shell resolver,
profile paths, examples, tests, release-pin validation and generated payload
use these names. The two redundant desktop environments were removed. There
are no compatibility aliases for the retired names. The unqualified NVMe and
eMMC desktop selections resolve directly to the canonical generic Btrfs and
x360 environments rather than to duplicate desktop files.

`-duo` is a suffix denoting preservation of other installed systems, not a limit
of two operating systems. Each duo class requires `addon/dualboot` (short token
`dualboot`). The existing `dualboot_efi=<slot>` and
`dualboot_debian=<first-Debian-slot>` arguments must identify the real layout.
The preservation path reuses the selected ESP and preserves existing slots
before the first Debian slot. It is not an arbitrary interleaved-partition OS
discovery or relocation feature. A missing preservation addon now causes a class
validation error rather than allowing the duo profile to become a whole-disk
installation. Back up the existing systems and verify slot numbers before any
unattended multi-OS installation.

See `d-i/forky/hosts/README.md` for composition order and selection details.

## 2. Disk model and capacity-dependent sizing

Both P15s profiles now use:

```sh
IOCOST_DEVICE_MODEL_MATCH="WDC PC SN730 SDBQNTY-512G-1001*"
```

The trailing wildcard tolerates the model-field padding reported by NVMe tools.
The transport, capacity, sector size and firmware columns are not part of the
model string. The firmware wildcard and the existing IOCost enable/disable and
performance policy are retained. The numeric IOCost parameters are explicitly
labelled provisional, not measurements of this SSD. Matching a model is not a
substitute for on-device calibration, and this revision does not execute a
benchmark or enable an otherwise disabled IOCost policy.

The existing dynamic algorithm is retained: read actual disk bytes, subtract
preserved extents and required overhead, honor filesystem minimums, distribute
the available budget toward profile preferences, and let root consume the
remaining recipe space. Raw-zram and swap limits remain bounded by the existing
RAM, media and profile policies. An undersized disk is rejected instead of
quietly creating a layout that cannot fit. Filesystem sizes need not all grow at
the same rate: a capped partition stays capped while other filesystems or root
grow. Partman uses decimal MB; RAM policies also contain explicitly named MiB
values. The code does not confuse the model's nominal 512 GB with real capacity.

The added matrix executes the production sizing code at 64, 128, 256, 512.11,
1024 and 2048 decimal GB, with 32 GiB RAM. It covers P15s normal and duo profiles;
the duo fixtures reserve 25 percent of the disk for existing systems. An 8 GB
fixture must fail. Existing tests cover the remaining profiles and their sizing
policies. Machine-readable planned values are in
`validation/2026-09-21-profile-zram-r6/capacity-examples.json`.

For illustration, the normal 512.11 GB fixture plans a root target of 89,275 MB
and a raw-zram target of 30,065 MB. At 1 TB, root grows to 601,165 MB while
raw-zram retains that cap. At 64 GB, raw-zram shrinks to 7,872 MB. These are recipe
targets before final alignment/remainder allocation, not claims about formatted
usable space or an installation performed on those disks.

## 3. The 17177 MB versus 17180 MB installation failure

The error compared the measured raw partition with a nominal decimal-MB target
using a fixed 2 MiB allowance. Inspection of Debian partman shows that the final
partition is created with the remaining free extent (`full`); previous partition
boundaries have already been aligned. Consequently the tail partition can
accumulate rounding differences from earlier boundaries rather than exhibiting
only one isolated boundary's rounding error [1].

The fix is restricted to the actual final raw-zram partition. The validator
receives its device path and verifies the persisted layout context: canonical
positive slot numbers, ordered Debian start/end slots, raw-zram equal to the
last slot, valid dualboot policy, and a bounded count of newly created
partitions. For that partition only, the allowance is:

```text
(newly created partition count + 2) * 1 MiB
```

A newly created ESP is counted for a normal installation; a reused ESP is not
counted for a duo installation. At most 32 newly created partitions are accepted,
so the allowance cannot exceed 34 MiB. The extra two MiB bound the outer boundary
and decimal-MB conversion effects. This is a bounded normal-alignment allowance,
not a disk-size percentage or a waiver of size checks. Invalid context fails
closed. Other raw partitions, including raw swap, retain the original 2 MiB
allowance. Oversized deviations are rejected as well as undersized deviations.

Regression cases include the reported 17,177 MB interval and 4 KiB rounding,
exact tolerance boundaries, both directions beyond the boundary, invalid slot
metadata, and normal-versus-reused ESP counting. They execute under dash, bash
and BusyBox. The installed zram setup still clamps backing allocation to the
actual mapped capacity minus its existing safety reserve. It does not turn the
nominal recipe number into permission to write beyond the real device.

No partition creation commands were executed during this review. Unusual disk
geometry that exceeds the bounded allowance still fails rather than being
silently accepted; a real d-i installation remains an acceptance check.

## 4. Zram pressure handling and workload efficiency

A material timing defect was corrected: the daemon converted seconds to
milliseconds before calling `IO::Poll::poll`, but that Perl API performs its own
conversion. A configured ten-second timeout could therefore last ten thousand
seconds in the absence of an event. The call now passes seconds directly,
verified with both the real IO::Poll implementation and a call-boundary test [2].
Cooldown and recovery timing use a monotonic clock, so wall-clock corrections
do not distort pressure decisions.

The daemon passes the actual pressure reasons to maintenance instead of
relabelling them as an operator override. The minimum logical-fill gate applies
to normal, opportunistic maintenance only. A genuine pressure or emergency pass
can proceed below that fill threshold, while preserving the existing cold-page,
tier, pass-size and kernel-quota restrictions. The existing nonblocking shared
lock prevents daemon and timer passes from overlapping. Cooldowns, hysteresis,
resource weights and the two-descriptor PSI model remain in place [3].

The post-maintenance metrics capture no longer performs another full block-state
candidate scan. Initial candidate discovery and its existing bounds are
retained. When authoritative block-state data is unavailable, a visible warning
explains why automatic targeted writeback is suppressed; bounded recompression
remains available. This deliberately avoids blind broad writeback under pressure.

Dry-run daily-budget refresh no longer writes sysfs or records the day as already
refreshed. A subsequent real run can still refresh its quota. Unsigned sysfs
attributes reject trailing garbage. Compaction no longer resets the lifetime
peak memory statistic on every pass; initialization retains its existing reset.
These changes do not increase the configured memory or I/O budgets.

## 5. Operational logging and writeback audit

The effective default log level is now `info` throughout installer defaults,
rendering, configuration schema and logger fallback. `debug` remains available
for cooldown/lock suppression details; routine polls do not emit noisy info
records. The existing route is retained:

```text
zram helper -> local Unix syslog / journal -> rsyslog
            -> /var/log/managed/zram/zram.log
```

Records cover setup activation and shutdown, PSI trigger registration, daemon
start/stop, pressure dispatch and recovery, maintenance reasons and fill levels,
non-authoritative telemetry, quota refresh, compaction, and recompress/writeback
operation start and result. Trigger records include a per-process operation ID,
a bounded specification and original specification length, monotonic elapsed
milliseconds, result, observed backing-write delta, observed memory-use delta,
and remaining kernel writeback quota.

`bd_writes_delta_4k` uses the kernel's fixed 4 KiB backing-statistics unit.
`backing_written_bytes` is that delta multiplied by 4096, independently of CPU
page size [4]. Padded kernel statistic fields are split without a leading empty
field, with a regression using the kernel's fixed-width format. Missing or reset
counters are reported as `unknown`, not fabricated
zeroes. `accepted` means the sysfs request succeeded; it does not claim every
candidate was written or memory was reclaimed. Concurrent swap activity may
contribute to the observed deltas, and these are not NAND-level physical-write
or SSD-endurance measurements. No page contents are logged.

The logger uses local Unix syslog only, limits each message to 4096 characters,
normalizes control characters to maintain one record per line, and preserves the
caller's error state. A failed local syslog send falls back to stderr captured by
systemd rather than disappearing. The existing managed-log route and rotation
retain root:adm access, mode 0640, directory mode 0750, daily rotation with four
rotations, maximum age seven days and an 8 MB rotation threshold. These are
rotation settings, not a hard byte cap between logrotate invocations.

Important retention limits remain: several profiles use tmpfs for `/var/log`;
the requested text log is then volatile across reboot. Journal retention follows
the existing journal policy. Rsyslog or journal rate limits can still drop
excessive traffic. This revision does not add remote archival or promise durable
forensic retention. The existing daily writeback-limit default is also unchanged;
kernel quotas and `/run` state reset with device initialization/reboot [4].

## 6. Process lifecycle and isolation

The scoped hardening concerns zram maintenance, not raw-device setup. Both
maintenance units retain private PID namespaces, full aggregate proc metrics,
control-group termination, bounded stop time, no-new-privileges, read-only system
files, private temporary space, memory and I/O limits. Both now have only
`CAP_SYS_RESOURCE` in the capability bounding set, namespace creation restricted,
and `OOMPolicy=stop`. The timer service gains the daemon's task-count and Unix
address-family bounds and setup-linked stop dependencies. `BindsTo`/`PartOf`
prevent it from outliving the setup service.

The maintenance AppArmor profile no longer grants blanket capabilities,
networking, mount/user-namespace access or arbitrary filesystem writes/execution.
It permits its Perl runtime, canonical configuration, aggregate memory/PSI
metrics, private runtime state, read-only device metadata and block-state
telemetry, local logging, and the exact required zram control attributes.
`CAP_SYS_RESOURCE` supports privileged PSI trigger windows; raw-device setup
keeps its separate existing privileges. Kernel-tunable or device hiding that
would break legitimate zram/PSI access was not added indiscriminately.

These controls implement a best-effort application of NIST SP 800-53 principles:
least privilege (AC-6), process isolation (SC-39), useful audit record content
(AU-3), and protection of audit data (AU-9). This is a design mapping, not a claim
of NIST compliance, complete control implementation or an independent assessment
[5, 6]. Same-user GUI services are not a security boundary against a fully
compromised desktop account, and root compromise is not solved by these changes.

The managed desktop application launcher and all 23 `labwc_managed_app` Python
modules are byte-for-byte unchanged. Existing transient-service collection,
control-group lifecycle, session membership, environment validation and shutdown
barriers are retained. All other target-side changes are zram-specific; the
shared AppArmor file changes only its zram-maintenance profile. Zoom and Discord
private Xwayland, compositor settings, Waybar/native menus and Crystal Dock
runtime files were not modified. The protected-file comparison is recorded in
`validation/2026-09-21-profile-zram-r6/protected-files.json`.

## 7. Verification evidence and acceptance boundary

Fresh evidence is under `validation/2026-09-21-profile-zram-r6/`. Its `summary.json`
is authoritative for stage exit codes, test counts, skips and audit categories.

The completed full run collected 2,340 tests: 2,291 passed and 49 were skipped.
The installer/runtime suite accounts for 2,161 cases (49 skipped); repository-tool
tests account for 179 cases (none skipped). Browser/generated-product checks,
59 preseed files, and 577 shell parser checks across 283 files passed. The added
21-case review suite also passed in a final focused rerun, including padded
kernel-statistics fields. Twelve separate real class-selection checks passed.

The static audit reports 472 passing checks, 180 structural passes, 157
checks blocked by dependencies, 11 blocked by tools, 509 inventory-only entries,
and two templates needing rendering. Its exit status does not turn those
blocked/inventory/template categories into runtime passes. `final-refresh.json`
records rebuilt-product verification after the final counter-parser refinement.

The new review suite exercises actual shell sizing and validation, actual logger,
sysfs and budget code with simulated kernel/configuration boundaries, and exact
daemon/maintenance methods. It does not replace a complete Moo-based runtime or
a live zram kernel. The AppArmor profile is parsed offline, not loaded/enforced.
Existing resource-policy tests retain original CPU, I/O and memory fingerprints;
only explicitly enumerated model/comment and zram-isolation deltas are reversed
for comparison. Deleted duplicate profiles are not allowed to overwrite the
canonical files' original provenance hashes.

A separate twelve-case check runs the real class resolver under dash and BusyBox:
canonical NVMe/eMMC/VM defaults resolve, the P15s duo class works with its addon,
the same class is rejected without it, and a retired identifier is rejected.
The check replaces only the fatal-hold boundary with process exit and does not
execute disk commands. Its result is in `class-selection.json`.

The validation container lacks several target Perl dependencies, including
Moo/MooX/Type::Tiny-related modules, and cannot activate the target systemd 261.2
services or exercise physical storage. Dependency-blocked checks, skipped tests,
inventory-only entries, unrendered templates and structural unit inspection are
not presented as successful runtime verification. No stress test, actual
writeback, rsyslog delivery, private-Xwayland GUI session or multi-OS installation
was performed here. Existing dated reports remain provenance, not fresh results.

The following target checks are read-only, except that the first helper command
validates configuration/runtime prerequisites; they do not deliberately force
writeback, reset a device, stop swap or repartition anything:

```sh
systemd --version
systemctl status zram-setup.service zram-writebackd.service zram-writeback.timer
systemctl show zram-writebackd.service zram-writeback.service \
  -p KillMode -p PrivatePIDs -p CapabilityBoundingSet -p RestrictNamespaces \
  -p OOMPolicy -p TasksMax -p MemoryMax
sudo /usr/local/libexec/zram-writeback validate-runtime
sudo /usr/local/libexec/zram-writeback status
sudo /usr/local/libexec/zram-writeback metrics
sudo tail -n 100 /var/log/managed/zram/zram.log
sudo journalctl -b -t zram-writeback
cat /sys/block/zram0/bd_stat /sys/block/zram0/mm_stat
sudo aa-status
```

On a disposable VM or backed-up test machine, also verify normal and duo d-i
installation, unchanged preserved partition boundaries, reboot activation,
pressure/recovery behavior, measured backing writes, journal-to-file delivery,
log rotation, and service/child cleanup during logout and shutdown. Inspect
AppArmor denials and kernel feature availability rather than broadening policy
blindly. Verify the running system's actual unit names/device suffix when local
configuration differs from the shipped defaults. Publish the entire rebuilt
served tree atomically, not a mixture of old profiles and a new payload.
