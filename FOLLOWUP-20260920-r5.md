# Revision 5 - Independent profile release pins

Starting point: complete Revision 4 repository. This release fixes the erroneous
cross-profile resctl-bench equality gate and applies the user's requested
resctl-bench URL and SHA-256 defaults. It does not change runtime desktop,
Waybar, power, AppArmor, Xwayland, package-selection or hardware policy.

## Corrected behavior

`tools/check_resctl_bench.py` previously validated each profile and then compared
its eight resctl-bench fields with the first profile. Any difference caused:

```text
resctl-bench pins differ from ...; update all profiles together
```

That comparison was an inappropriate restriction on independent profiles. It is
removed, not bypassed through an optional flag or hidden fallback. There is no
reference profile and no release-value synchronization step. Normal `make build`
and build `--check` use the same corrected validator.

`reported-case-reproduction.json` exercises the actual R4 checker with the exact
reported profile names: `btrfs-de-flex-duo.env` retains the old pins while
`f2fs-de-hp14.env` uses the newly supplied URL/SHA-256. R4 produces the exact
reported two-field error. R5 accepts both profiles without rewriting either.

Every profile may now choose a different valid resctl-bench URL, SHA-256, tag,
version, download limit, expansion limit and member limit. The existing supported
origin and amd64 architecture policy remain unchanged. A profile's URL still
needs to agree with that profile's own tag/version/architecture; it does not need
to agree with any other profile.

Tomat's build validator already validated profiles independently. Its production
code is unchanged. Regression tests now explicitly prove that multiple profiles
can simultaneously use different valid Tomat tags, URLs and SHA-256 values too.

## Exact shipped defaults

Each of the 13 profiles under `d-i/forky/hosts/profiles/` contains:

```sh
RESCTL_BENCH_URL="https://github.com/mjcramerz/resctl-bench/releases/download/resctl-bench-v0.0.2-P15s/resctl-bench-2.2.6-x86_64-unknown-linux-gnu-native-fe7971477fed192a.tar.gz"
RESCTL_BENCH_SHA256="5521053cd583b6d01c608a9deff7dabe4ebb5e07eb314d8819a9833ff5684d12"
```

The existing `RESCTL_BENCH_TAG="resctl-bench-v0.0.2-P15s"` and
`RESCTL_BENCH_VERSION="2.2.6"` already match this artifact and are retained.
Only the URL and SHA-256 lines change in each profile. All other profile bytes,
including Tomat pins, resource limits and enable flags, remain unchanged.

These are the defaults in this delivery, not mandatory global values. Changing
one profile does not require changing any other profile or editing the checker.
Change that profile's related fields coherently, then rebuild the generated
payload. The offline build checks configuration structure, not whether a
syntactically valid digest actually matches a remote archive.

## Safety checks retained

The checker still reads bounded regular profile files as literal data; it never
sources them as shell. Missing, duplicate, unknown and nonliteral assignments
remain errors. Each profile is validated through the actual target installer's
existing policy, including release URL structure, its own tag/version agreement,
SHA-256 format, supported architecture and size/member bounds. Invalid later
profiles are not skipped just because an earlier profile is valid.

The target's `resctl-bench-install.py` and `resctl-bench.sh` are byte-identical to
Revision 4. Actual downloaded bytes still have to match the selected profile's
SHA-256 before archive processing or installation. Archive inventory, member
hashes, path/link/type restrictions, size bounds, ELF checks, unprivileged target
smoke probes, private staging and publication/rollback checks are unchanged.
No downloaded installer is executed and no target build-from-source path is added.

## Regression coverage

The new `test_profile_pin_independence_20260920.py` contains nine tests. A real
build integration test copies the build inputs into an isolated temporary
repository, assigns **13 different pin sets to both resctl-bench and Tomat**, and
runs the real `make build` and `make check` commands. It verifies that the builder
does not rewrite any profile and that each distinct profile's exact bytes and
hash reach the generated payload and manifest. Introducing one malformed digest
then makes both commands fail without replacing any generated product.

Other tests exercise one-profile-only changes, order independence, consistency
within each profile, rejection of invalid later profiles, retained origin,
architecture and resource bounds, and the real resctl shell dispatcher under
Dash and BusyBox. All eight fields reach the intercepted target command exactly
as configured in the selected profile, without reusing a previous profile's pins.
Alternate release numbers, URLs and digests are clearly synthetic test inputs;
they are not shipped profile values or claims that those releases exist.

Existing tests which imposed a repository-wide fixed release now validate each
actual profile independently. Tests using historical synthetic download fixtures
retain those fixtures. The shell-staging assertion now compares against the
actual selected profile instead of an obsolete global digest. The workload
preservation test excludes only the same three-key Tomat release-pin block, not
a specific version, while keeping its original workload hash fixtures unchanged.

## Verification boundaries

The exact URL and SHA-256 were supplied by the user and preserved as requested.
The container could not resolve GitHub during the attempted download, so the
vendor archive was **not independently downloaded or hashed here**. The separate
web release listing returned older asset metadata and the requested binary/API
could not be fetched. That is not evidence that the requested new artifact is
absent. No fallback URL or replacement checksum was substituted.

A booted Debian Forky/systemd 261.2 unattended installation was not performed.
Target network availability, the actual release bytes and native CPU/loader
compatibility still require the existing on-target validation. This revision's
completed build and tests establish profile independence and publication
integrity, not a blanket guarantee of physical-host installation success.

## Use and reproduction

Use the complete Revision 5 repository, or carefully merge the included source
diff into a working tree with local changes. From the repository root:

```sh
make build
make check
python3 -B tools/check_preseeds.py
python3 -B validation/profile-pin-independence-20260920-r5/verify-payload.py
PYTHONDONTWRITEBYTECODE=1 python3 -B validation/profile-pin-independence-20260920-r5/run-tests.py --suite focused
PYTHONDONTWRITEBYTECODE=1 python3 -B validation/profile-pin-independence-20260920-r5/run-tests.py --suite tools
```

Build output now says:

```text
resctl-bench: 13 profiles have independently valid release pins (offline)
```

Publish `preseed.cfg`, `payload.tar.gz`, `payload.manifest` and the associated
repository tree atomically. Profile changes require rebuilding before
publication. Updating the served files does not replace a payload already
loaded into a running installer; use a fresh installer session for the new tree.

Evidence is under `validation/profile-pin-independence-20260920-r5/`, including
baseline failure reproduction, source diff, mixed-profile regression results,
full tools results, payload verification, exact shipped pins and scope checks.
